- v2 media data lives in child tables (song_lyrics, song_audio_versions, song_videos) keyed by song + language; songs columns stay as legacy defaults — why: non-destructive multi-language extension.
- Motion artwork lives in song_motion_artwork rather than songs or song_videos — why: keep short muted artwork separate from full-length Video mode media.
- Games/challenge presentation (hub cards, banner, challengeStats) uses app_settings with shared listener/CMS preview components; effects scoped under games-interactive / challenge-arcade CSS; operational values stay in challenges; milestone gates and prize eligibility are computed only by supabase/functions/_shared/challengeMilestones.ts, imported by the app and the record/finalize functions — why: CMS styling never alters game rules or prizes, and players see exactly the rules the server enforces.
- Plays are logged only via the record_play RPC into play_events (no client inserts); discovery reads go through get_trending/get_quick_picks/get_daily_discover — why: privacy and consistent counters.
- Playback continuity is stored locally and restored paused without logging a new play — why: preserve position across navigation and app exits without inflating analytics.
- Stem separation runs through a queue in song_audio_versions (kind='instrumental' is the job row), processed by the stem-worker function on a cron that arms on enqueue and unschedules when drained — why: bounded, single-flight, retry-safe background AI work with a persisted pause on billing errors.
- Song, Karaoke, mini-player, and Video playback timelines use the shared PlaybackProgress component — why: progress tracks and position markers must remain visually consistent.
- Lists start whole-list queues; Video advances in upNextOrder (src/lib/videoQueue.ts), the order Up Next lists; queue edits only via src/lib/queueOps.ts; Karaoke skips songs lacking a backing track; src/lib/autoContinue.ts extends a done queue in the same mode — why: continuous play, shown order is played order.
- Admin-managed look, home layout and Stage Mode media/overrides live in app_settings via src/lib/siteSettings.ts (Stage's shared background library + font list in src/lib/stageBackgrounds.ts; listener picks in localStorage); playlist card colours in playlists.card_color — why: no hardcoded styling, CMS controls it.
- Renewal reminders are milestone-deduped in renewal_reminders and sent by the process-expired-subscriptions function (in-app notifications + OneSignal push); the home RenewalBanner only reads subscription state — why: one reminder per milestone, no client-side dupes.
- Community data (communities, members, posts, likes, comments) is members-only via is_community_member/can_view_community_post (admin override), counts via get_community_member_counts, inserts throttled by enforce_community_rate_limit; moderators live in community_moderators, assigned only by admin-validated RPCs (membership roles grant no moderation); card colours in app_settings by community ID — why: private, spam-resistant communities; presentation separate from authorization.
- Play taps start audio synchronously, never after an await: PlayerContext preloads the preferred language's ready song_audio_versions map (src/lib/preferredLanguage.ts) and swaps lyrics in later; tap-driven saves update the screen first and ignore repeat taps — why: phones block sound started outside the tap; slow feedback causes double taps.
- Optional listener features use the shared FeatureProvider and featureFlags registry backed by individual app_settings keys; reuse existing keys, gate routes/navigation/player actions, refresh after admin writes, on return to screen (throttled) and every few minutes, keep admin CMS access — why: consistent switches without duplicate settings or polling; switches are presentation, not server authorization.
- Lists that can exceed 1,000 rows (songs, pickers, admin tables) load through fetchAllRows in src/lib/fetchAll.ts with a stable `.order("id")` tiebreaker; no new background polling under 1 minute, RLS policies wrap auth.uid()/has_role in `(SELECT ...)` — why: the backend caps each request at 1,000 rows, and per-row checks and tight polling are the main load at scale.
- The referral switch is enforced server-side by referrals_enabled() in referral RPCs/trigger; invite codes resolve via resolve_invite_code (account id, or a username only when unique) — why: not client-bypassable, never credit the wrong person.
- Online content search goes through the search_content RPC (weighted simple+unaccent tsvector, trigram titles) via src/lib/contentSearch.ts with a shared 250 ms debounce; client-side fuzzy filtering is only for the offline downloads library — why: one consistent multi-language ranking everywhere.
- The mini player's hidden state lives in src/lib/playerVisibility.ts (usePlayerHidden, localStorage), read by PlayerBar and AppLayout — why: bottom spacing shrinks with the player and the choice survives reloads.

- Subdirectories may have their own AGENTS.md (e.g. src/lib/secureDownloads, supabase/functions, src/components/home); read it before changing files there.
- Pasted song-video links are checked by the resolve-video-url function (admins/editors) before saving: KingsSpace watch pages resolve to their direct video file and web pages are rejected — why: song_videos.video_url must always be a playable file or YouTube link.
- Free-song access (songs.is_free_download) is decided client-side by canUseSong/isFreeSong in src/lib/freeSongs.ts, which also checks an on-demand cached set of free song IDs; offline entitlement stays server-side in offline-media — why: many lists build player songs without the flag, and the server remains the authority for saves.
- Privileged fields are protected by BEFORE triggers (guard_profile_privileged_cols, guard_pending_insert, guard_editor_song_update) that bypass only for admins and backend jobs (auth.uid() NULL); RLS alone doesn't stop users editing columns on their own rows — why: balances, request approvals and song identity must not be self-set.
- The OneSignal web worker lives at public/push/onesignal/ with its own scope (set in index.html init) — why: sharing scope "/" would replace the app's /serviceworker.js.
- Rhapsody Daily is read live from read.rhapsodyofrealities.org (window.dailyDevotional) in src/lib/rhapsodyDaily.ts, sanitised, cached locally, with the rhapsody-daily function as fallback — why: no copy to maintain, new day appears on refresh.
- The free trial is once per account: the mark_trial_used trigger rejects starting or extending a trial once trial_used_at is set, for everyone — why: subscription_plan resets on expiry, so it cannot prove a trial was used.
- Command Centre figures come from the admin-only admin_command_centre/admin_referral_stats RPCs (SQL aggregates, expired plans = free, instrumentals excluded from lyric/karaoke gaps); plays log mode song/karaoke/video; countries come from user_activity_days (one row per user per UTC day via log_activity_day; no IPs stored) — why: client fetches cap at 1,000; profiles hold church regions, not countries.
- Voice search records 16 kHz WAV, transcribes via the voice-search function (signed-in only) and ranks with search_voice (word-pair coverage, tolerates misheard words) — why: spoken lines are long and imperfect.
- Sign-up and password-reset emails link straight to /auth/confirm and /reset-password with a token_hash (auth-email-hook/recoveryLink.ts), and those pages verify only after the person taps a button — why: email link scanners (seen in logs) were using up one-time tokens before the real click.
- Clearing a challenge ladder goes only through the admin-only reset_challenge_leaderboard RPC, which snapshots standings into challenge_leaderboard_archives before wiping scores, game logs, bonuses and challenge invites (entries are kept) — why: reused challenges restart at zero without losing past winners.
- Social share URLs are built only by src/lib/socialShare.ts — why: one tested place keeps each app's official format.
